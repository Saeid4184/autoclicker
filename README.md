# AutoClicker Pro — فاز ۳ تا ۹

## 🔍 بازبینیِ باگ (این نسخه) — چی پیدا و رفع شد

پروژه رو کامل خوندم (همه‌ی فایل‌های Kotlin/XML/Gradle). این‌ها باگ‌های واقعی‌ای بودن که پیدا و رفع شدن:

1. **لیک فایل الگوی تصویری در سناریوی کپی‌شده (`ScenarioStore.duplicateScenario`)** — قبلاً برای هر قانون IMAGE فقط `matchValue` (الگوی اولویت ۱) مستقل‌سازی می‌شد، ولی `imageTemplatePaths` (الگوهای اضافه‌ی فاز ۹) هنوز به فایل‌های سناریوی اصلی اشاره می‌کرد. یعنی همون کلاس باگی که کامنت کد می‌گفت «قبلاً رفع شده» (اشتراک فایل بین سناریوی اصلی و کپی‌اش)، برای فیلد جدیدتر دوباره وجود داشت. حالا `copyTemplate` برای هر آیتم `imageTemplatePaths` هم صدا زده می‌شه.
2. **لیک فایل موقع حذف قانون/سناریو (`RulesActivity`, `ScenariosActivity`)** — حذف یک قانون IMAGE یا کل یک سناریو فقط فایلِ `matchValue` رو پاک می‌کرد؛ فایل‌های `imageTemplatePaths` هیچ‌وقت پاک نمی‌شدن و برای همیشه در حافظه‌ی داخلی اپ می‌موندن. یک تابع مشترک `TemplateStore.deleteAllTemplatesFor(rule)` اضافه شد که هر دو رو پاک می‌کنه، و هر دو صفحه ازش استفاده می‌کنن.
3. **صفحه‌ی اصلی بدون اسکرول (`activity_main.xml`)** — با اضافه‌شدن دکمه‌های فاز ۵-۹ (ضبط‌ها، تاریخچه، سناریوها، ...) تعداد آیتم‌ها به ۹ رسیده؛ چون ریشه‌ی layout یک `LinearLayout` ساده با `gravity=center` و بدون `ScrollView` بود، روی گوشی‌های کوچیک یا با تنظیم «اندازه‌ی فونت بزرگ‌تر»، دکمه‌های پایینی (مثلاً «تاریخچه‌ی اجرا») می‌تونستن کاملاً غیرقابل‌دسترس بشن. حالا همه‌چیز داخل `ScrollView` قرار گرفته.
4. **کارایی `RunLogStore` (بهینه‌سازی، نه باگ اساسی)** — برخلاف بقیه‌ی storeها (`ScenarioStore`/`RecordingStore`)، این یکی هیچ کش درون‌حافظه‌ای نداشت: هر بار که یک قانون اجرا می‌شد (روی ترد اصلی، همون لحظه‌ی کلیک/سوایپ)، کل تاریخچه (تا ۳۰۰ ردیف) از SharedPreferences دوباره خونده، پارس، و بازنویسی می‌شد. حالا مثل بقیه‌ی storeها یک‌بار لود می‌شه و فقط append انجام می‌گیره.

چیزهایی که باگ نبودن ولی محدودیتِ ذاتی پلتفرمن (نیازی به اقدام نیست، فقط برای آگاهی):
- پخشِ یک Recording با `GestureDescription` سرعتِ واقعیِ بین نقاطِ میانیِ یک لمس رو حفظ نمی‌کنه (فقط شکل مسیر + مدت کل)؛ محدودیت خودِ API اندرویده.
- انتخاب‌گرهای رنگ‌پیکسل/الگوی تصویری از یک فریمِ لحظه‌ی بازکردن منو استفاده می‌کنن، نه لحظه‌ی دقیقِ لمس — اگه صفحه‌ی زیرین بین این دو لحظه عوض بشه (مثلاً یک انیمیشن)، ممکنه رنگ/الگوی گرفته‌شده دقیقاً همون چیزی نباشه که در لحظه‌ی لمس دیده می‌شده.

# AutoClicker Pro — فاز ۳ تا ۹

## فاز ۹ — زنجیره‌ی شرطی، تاخیر تصادفی، انتظار برای ناپدیدی، چند الگوی تصویری، رنگ پیکسل، OCR

شش قابلیت درخواستی، همه روی همون معماری قبلی (RuleModels/ScenarioStore/ClickAccessibilityService/OverlayService) سوار شدن؛ هیچ‌کدوم رفتار قوانین قدیمی‌تر (فاز ۱-۸) رو عوض نمی‌کنن، چون همه‌ی فیلدهای جدید مقدار پیش‌فرضِ خنثی دارن.

### 1) زنجیره‌ی شرطی («اگه X دیدی → Y، وگرنه → Z»)
- `ClickRule.elseRuleId`: id یک قانون دیگه‌ی همون سناریو. اگه شرط قانونِ اصلی برقرار نشد، همون دور حلقه، فوراً قانونِ elseRuleId اجرا می‌شه.
- از دیالوگ «⚙ تنظیمات پیشرفته» (دکمه‌ی جدید کنار هر قانون در «مدیریت قوانین کلیک») با یک Spinner قابل انتخابه.
- سقفِ عمقِ زنجیره ۸ هاپه و تشخیص حلقه (A→else=B، B→else=A) داره: به‌محض برخورد دوباره به یک قانون در همون دور، زنجیره متوقف می‌شه (بدون کرش، بدون حلقه‌ی بی‌نهایت). جزئیات در `maxElseChainDepth`/`visited` داخل `ClickAccessibilityService.attemptClickRule`.
- lookup قانونِ else هم O(1) هست: `OverlayService` هر تیک یک `Map<id, ClickRule>` می‌سازه و پاس می‌ده، نه یک لیست که هر hop باید کامل اسکن بشه.

### 2) تاخیر تصادفی بین کلیک‌ها
- `postClickDelayMinMs` / `postClickDelayMaxMs`: بعد از هر بار اجرای قانون، یک عدد تصادفیِ یکنواخت بین این دو مقدار صبر می‌شه، جدا و اضافه بر فاصله‌ی ثابتِ حلقه (`loopIntervalMs`).
- تا وقتی این تاخیر در جریانه، همون قانون در دورهای بعدیِ حلقه رد می‌شه (busy-guard) تا کلیک تکراری نخوره.

### 3) «منتظر بمون تا ناپدید بشه»
- `waitForDisappearAfterClick` + `waitForDisappearTimeoutMs` + `waitForDisappearPollMs`: بعد از کلیک، هر چند صد میلی‌ثانیه دوباره همون شرط چک می‌شه؛ به‌محض ناپدید شدنِ هدف (یا رسیدن به سقف زمانی) قانون آزاد می‌شه.
- با تاخیر تصادفیِ بالا قابل ترکیبه (اول صبر برای ناپدیدی، بعد تاخیر تصادفی اضافه).

### 4) چند الگوی تصویری با اولویت
- `ClickRule.imageTemplatePaths: List<String>`: به ترتیب همین لیست (ایندکس ۰ = بالاترین اولویت) چک می‌شن؛ اولین تطابق موفق با `threshold` انتخاب می‌شه.
- از منوی دکمه‌ی شناور: «➕ افزودن الگوی تصویری دیگر به یک قانون تصویری (اولویت)» — یک قانون IMAGE موجود رو انتخاب می‌کنی، دور الگوی جدید (با اولویت پایین‌تر از قبلی‌ها) می‌کشی.
- Export/Import سناریو (فاز ۶) هم آپدیت شد: همه‌ی الگوهای اضافه هم به‌صورت Base64 داخل JSON جاسازی می‌شن، نه فقط الگوی اصلی.

### 5) تشخیص رنگ پیکسل در یک نقطه‌ی خاص
- نوع تشخیص جدید `MatchType.PIXEL_COLOR` + فایل جدید `PixelColorMatcher.kt`: به‌جای matchTemplate روی کل تصویر، فقط `getPixel(x, y)` از فریم گرفته‌شده رو با `targetColorHex` (با تحمل `colorTolerance`، ۰ تا ۲۵۵ در هر کانال) مقایسه می‌کنه — خیلی سبک‌تر از تطابق تصویری کامل.
- از منوی دکمه‌ی شناور: «🎨 رنگ پیکسل در یک نقطه‌ی خاص» — روی نقطه‌ی موردنظر تپ می‌کنی، رنگ همون لحظه از فریم نمونه‌برداری و ذخیره می‌شه.

### 6) OCR — خوندن متن روی صفحه (امتیاز، وضعیت و...)
- نوع تشخیص جدید `MatchType.OCR_TEXT` + فایل جدید `OcrMatcher.kt`، با **ML Kit Text Recognition** (`com.google.mlkit:text-recognition:16.0.1` — مدل on-device، داخل خودِ APK باندل می‌شه، نیازی به گوگل‌پلی‌سرویسِ زنده یا اینترنت حین اجرا نیست؛ فقط حین Gradle Sync دیپندنسی دانلود می‌شه، دقیقاً مثل OpenCV).
- `ocrRegion` (اختیاری، "left,top,right,bottom") ناحیه‌ای رو که باید OCR بشه محدود می‌کنه (سریع‌تر و دقیق‌تر از OCR کل صفحه). `matchValue` متنیه که باید داخل نتیجه‌ی OCR پیدا بشه (contains، بدون حساسیت به بزرگ/کوچکی حروف).
- `ocrClickPoint` (اختیاری، "x,y") نقطه‌ی کلیک رو مشخص می‌کنه؛ اگه خالی باشه، مرکز `ocrRegion` کلیک می‌خوره.
- از منوی دکمه‌ی شناور: «🔤 OCR: کلیک وقتی متنی خاص دیده شد» — دور ناحیه می‌کشی، متن هدف رو تایپ می‌کنی.
- **کار می‌کنه با Unity/Cocos/هر موتور دیگه‌ای، بدون هیچ تنظیم اضافه‌ای.** دلیلش: بر خلاف TEXT/VIEW_ID (که از UI Tree اکسسیبیلیتیِ اندروید می‌خونن — چیزی که اپ‌های Unity/Cocos چون همه‌چیز رو مستقیم روی یک Canvas/OpenGL می‌کشن اصلاً پرش نمی‌کنن)، OCR دقیقاً مثل IMAGE از `ScreenCaptureService.latestFrame` (اسکرین‌شاتِ خام گرفته‌شده با MediaProjection) می‌خونه — یعنی به موتور رندرِ زیرینِ اپ کاملاً بی‌ربطه؛ هر چیزی که چشمِ خودت روی صفحه می‌بینه، OCR هم می‌بینه.
- **بهینه‌سازیِ پیش‌پردازش برای فونت‌های بازی**: `ocrPreprocess` (پیش‌فرض `true`) قبل از OCR، ناحیه رو خاکستری+کنتراست‌دارتر می‌کنه و اگه کوچیک باشه بزرگ‌نمایی می‌کنه (`OcrMatcher.preprocessForOcr`). فونت‌های Unity (خصوصاً TextMeshPro با outline/سایه/گرادیان، یا فونت‌های پیکسلیِ ریز) معمولاً کنتراست ساده‌ای با پس‌زمینه ندارن و دقتِ ML Kit روشون بدون این پیش‌پردازش پایین‌تره. از «⚙ تنظیمات پیشرفته» قابل خاموش‌کردنه اگه یک مورد خاص با پیش‌پردازش بدتر شد (نادره، ولی ممکنه).
- **نکات عملی برای گرفتن نتیجه‌ی بهتر روی محیط‌های Unity:**
  - ناحیه‌ی OCR رو تا حد امکان تنگ دور خودِ متن بکش (نه یک باکس بزرگ که کلی پس‌زمینه/آیکون هم توشه) — نویزِ اطراف دقتِ تشخیص رو پایین می‌آره.
  - اگه امتیاز/عدد مدام در حال انیمیشن (بزرگ‌شدن، لرزش، fade) هست، یا OCR رو با `waitForDisappearAfterClick`/تاخیر ترکیب کن تا وقتی متن روی صفحه «آرومه» چک بشه، یا `loopIntervalMs` رو کمی بالا نگه‌دار.
  - اگه اپ `FLAG_SECURE` داشته باشه (بعضی بازی‌های آنتی‌چیت‌دار)، نه IMAGE نه OCR کار نمی‌کنن، چون MediaProjection اصلاً فریمی نمی‌گیره — این محدودیتِ سیستم‌عاملِ اندرویده، نه چیزی که از این اپ قابل دور زدن باشه.

### تغییرات فنی مهم‌تر
- منطق تشخیصِ `ClickAccessibilityService` به یک تابع واحد `matchRule()` (callback-based) بازنویسی شد که همه‌ی انواع MatchType (شامل انواع جدید) رو پوشش می‌ده و هم برای کلیک واقعی، هم برای چک «آیا هنوز هست» (در waitForDisappear) استفاده می‌شه.
- یک `busyRuleIds` جدید جلوی کلیک تکراریِ یک قانون رو، وقتی داره منتظر ناپدیدی/تاخیر تصادفی می‌مونه، می‌گیره.
- `ScenarioStore.updateRule()` (و `RuleStore.update()`) برای اولین بار اضافه شد — قبلاً راهی برای جایگزینیِ کامل یک قانونِ موجود (لازم برای دیالوگ تنظیمات پیشرفته) وجود نداشت.

⚠️ مثل فازهای قبل، بدون Android Studio/گوشی واقعی build و تست نشده — مخصوصاً بخش OCR (ML Kit) که یک دیپندنسیِ کاملاً جدیده و اولین Gradle Sync بعد از این تغییر به دانلود بسته‌ی مدل نیاز داره.

## فاز ۸ — تاریخچه‌ی اجرا (لاگ)

- یک آبجکت جدید `RunLogStore` هر بار که `performAction` در
  `ClickAccessibilityService` صدا زده بشه (چه کلیک واقعی، چه در حالت
  آزمایشیِ فاز ۷) یک ردیف ثبت می‌کنه: ساعت، برچسب قانون، نوع تشخیص، نوع
  اکشن، مختصات، و اینکه dry-run بوده یا نه.
- فقط ۳۰۰ ردیفِ آخر نگه‌داشته می‌شه (قدیمی‌تر خودکار حذف می‌شه) تا
  SharedPreferences بی‌نهایت بزرگ نشه.
- صفحه‌ی جدید «تاریخچه‌ی اجرا» (از منوی اصلی اپ) لیست رو از جدید به قدیم
  نشون می‌ده؛ ردیف‌های 🧪 یعنی حالت آزمایشی بودن و کلیک واقعی نخوردن.
  دکمه‌ی «پاک کردن تاریخچه» هم هست.
- این مکمل مستقیم حالت آزمایشیه: Toast لحظه‌ای فاز ۷ فقط همون لحظه رو
  نشون می‌ده، ولی این صفحه کل تاریخچه رو قابل مرور می‌کنه — هم برای
  دیباگ قوانین جدید، هم برای فهمیدن اینکه یک سناریوی واقعی دقیقاً چند
  بار و کِی اجرا شده.

⚠️ مثل فازهای قبل، بدون Android Studio/گوشی واقعی build و تست نشده.

## فاز ۷ — اولویت دستی قوانین + حالت آزمایشی (Dry-run)

### 📶 اولویت دستی قوانین
- دکمه‌های ▲/▼ در «مدیریت قوانین کلیک» ترتیب قانون رو در لیست سناریوی
  فعال جابه‌جا می‌کنن (`ScenarioStore.moveRuleUp/Down`). حلقه‌ی کلیک دقیقاً
  به همون ترتیب چک می‌کنه — مهم وقتی چند قانون IMAGE هم‌زمان فعالن.

### 🧪 حالت آزمایشی (Dry-run)
- از منوی دکمه‌ی شناور روشن/خاموش می‌شه. وقتی روشنه، هیچ ژست واقعی
  dispatch نمی‌شه؛ فقط Toast می‌گه کدوم قانون کجا می‌خواست کلیک بزنه.
  دکمه‌ی شناور هم آیکونش به 🧪 تغییر می‌کنه تا یادت نره روشنه.

⚠️ مثل فازهای قبل، بدون Android Studio/گوشی واقعی build و تست نشده.

## فاز ۶ — سوایپ به‌عنوان اکشن + Export/Import سناریو

دو آیتم از «نقشه فازهای بعدی» فاز قبل پیاده‌سازی شدن:

### ➡️ اکشن SWIPE
- `ActionType` حالا سه مقدار داره: `CLICK`, `LONG_PRESS`, `SWIPE`.
- برای هر نوع قانون (COORDINATE/TEXT/VIEW_ID/IMAGE) وقتی actionType روی
  SWIPE باشه، **مبدأ** سوایپ همون نقطه‌ای‌ست که matchType پیدا می‌کنه
  (مختصات ثابت خودِ قانون، یا مرکز المان/تصویر تشخیص‌داده‌شده)، و **مقصد**
  از فیلد جدید `swipeEndValue` ("x,y") خونده می‌شه.
- از منوی دکمه‌ی شناور، گزینه‌ی «➡️ سوایپ بین دو نقطه‌ی ثابت» یک قانون
  COORDINATE با actionType=SWIPE می‌سازه: اول نقطه‌ی مبدأ رو لمس کن، بعد
  نقطه‌ی مقصد رو — `ClickAccessibilityService.performSwipe` با
  `swipeDurationMs` (پیش‌فرض ۳۰۰ میلی‌ثانیه) اجراش می‌کنه.
- اگه `swipeEndValue` غایب/نامعتبر باشه (مثلاً یک قانون خیلی قدیمی که این
  فیلد رو نداره ولی دستی actionType‌اش SWIPE شده)، هیچ ژستی اجرا نمی‌شه؛
  فقط یک لاگ هشدار ثبت می‌شه — نه کرش، نه کلیک اشتباه.

### 🗂 Export/Import سناریو با JSON
- توی صفحه‌ی «مدیریت سناریوها»، هر سناریو یک دکمه‌ی «خروجی» داره: یک JSON
  کامل (اسم، فاصله‌ی زمانی، همه‌ی قوانین) از طریق منوی اشتراک‌گذاری اندروید
  (`ACTION_SEND`, متن ساده) می‌فرسته.
- دکمه‌ی «↓ ورودی از JSON» بالای لیست، یک دیالوگ با فیلد چندخطی باز می‌کنه
  که می‌تونی JSON رو پیستش کنی؛ یک سناریوی **جدید** (با idهای کاملاً تازه،
  کنار سناریوهای موجود، بدون جایگزینی چیزی) ساخته می‌شه.
- برای قوانین از نوع IMAGE، چون مسیر فایل تصویر محلی (matchValue) روی
  گوشیِ مقصد بی‌معنیه، خودِ فایل PNG الگو به‌صورت Base64 داخل همون JSON
  جاسازی می‌شه — یعنی JSON یک سناریوی پر از قانون تصویری می‌تونه حجیم بشه؛
  بعضی اپ‌های مقصدِ اشتراک‌گذاری ممکنه متن خیلی بزرگ رو رد کنن (محدودیت
  خودِ Android Intent، نه این اپ). اگه هنگام Import، تصویر Base64 پیدا یا
  دیکد نشه، قانون IMAGE به‌صورت **غیرفعال** وارد می‌شه (نه حذف) تا کاربر
  بفهمه باید دوباره الگو رو بگیره.

⚠️ مثل فازهای قبل، این کد هم بدون Android Studio/گوشی واقعی build و تست
نشده؛ قبل از اعتماد کامل امتحانش کن — مخصوصاً مسیر Import روی JSON دستکاری‌شده.

## فاز ۵ — ضبط کن، بعد دقیقاً همون‌جوری پخش کن

این قابلیت با همه‌ی قابلیت‌های قبلی (که «اگه فلان دکمه/تصویر رو دیدی، کلیک
کن» هستن) فرق داره: اینجا هیچ تشخیصی در کار نیست. فقط **دقیقاً همون کاری که
تو با انگشتت روی صفحه انجام می‌دی** — با همون مختصات و همون فاصله‌ی زمانیِ
واقعی بین لمس‌ها — ضبط و بعداً عیناً تکرار می‌شه.

**چطور کار می‌کنه:**
1. از منوی دکمه‌ی شناور، «⏺ ضبط حرکات لمسی» رو بزن.
2. یک لایه‌ی شفاف روی کل صفحه باز می‌شه. حالا هر تپ، سوایپ یا درگی که با
   انگشتت انجام بدی، با زمان دقیقش ثبت می‌شه (`ClickAccessibilityService`
   همون لحظه اون لمس رو دوباره روی اپ زیرین هم اجرا می‌کنه، تا حین ضبط هم
   بازی/اپ واکنش نشون بده).
3. با دکمه‌ی قرمز «⏹ پایان ضبط» (بالا-راست صفحه) ضبط رو تموم کن و یک اسم
   براش بذار.
4. هر وقت خواستی، از منوی دکمه‌ی شناور («▶ پخش یک ضبط ذخیره‌شده») یا از
   صفحه‌ی «ضبط‌های لمسی» در اپ اصلی، دقیقاً همون توالی رو با همون فاصله‌ی
   زمانیِ بین لمس‌ها دوباره اجرا کن (`ClickAccessibilityService.playRecording`
   با `GestureDescription.StrokeDescription` و `startTime` نسبیِ هر لمس).

**محدودیت‌های مهمی که باید بدونی:**
- حین خودِ ضبط، چون این لایه‌ی شفاف لمس رو می‌گیره و بعد دوباره اجراش
  می‌کنه، یک تپ ساده تقریباً بی‌تاخیره ولی یک سوایپ/درگ رو اپ زیرین فقط
  *بعد از* برداشتن انگشت می‌بینه (نه هم‌زمان با کشیدنش). این محدودیتِ روش
  بدون‌روتِ اندرویده (اندروید تا نسخه ۱۳ راه عمومی‌ای برای فقط-دیدنِ لمس
  بدون گرفتنش نداره) — نه باگ. خودِ فایلِ ضبط‌شده و پخشِ بعدی‌اش این تاخیر
  رو اصلاً نداره و کاملاً روان و هم‌زمان با زمان‌بندی اصلیه.
- اگه بازی صفحه‌ش رو با `FLAG_SECURE` محافظت کنه یا اصلاً حساس به دقتِ
  میلی‌ثانیه‌ای چندلمسیِ هم‌زمان باشه، ممکنه این روش جواب ندهد.
- ضبط‌های خیلی طولانی/پرتراکم به‌صورت خودکار به چند دسته شکسته می‌شن (به
  خاطر سقف مدت/تعداد استروکِ خودِ اندروید در `GestureDescription`)؛
  زمان‌بندیِ داخل هر دسته دقیقه، فقط دقیقاً سرِ مرز دو دسته ممکنه یک گسست
  خیلی کوچیک باشه.
- مثل بقیه‌ی قابلیت‌ها، این هم روی هر گوشی واقعی (بدون روت) کار می‌کنه؛
  دیتای ضبط‌شده در SharedPreferences همون اپ ذخیره می‌شه.

⚠️ کدهای این فاز هم مثل فازهای قبل این‌جا نوشته شده ولی بدون Android
Studio/گوشی واقعی build و تست نشده؛ قبل از اعتماد کامل، حتماً روی چند
سناریوی واقعی امتحانش کن.

## چی جدید اضافه شد؟ (فاز ۳ و ۴)

### 🖼 تشخیص تصویری با OpenCV (fallback وقتی UI Tree جواب نمی‌ده)
- یک سرویس جدید (`ScreenCaptureService`) با `MediaProjection API` هر فریم صفحه رو می‌گیره.
- از منوی دکمه‌ی شناور، گزینه‌ی «🖼 تشخیص تصویری با OpenCV» رو انتخاب کن → دور دکمه/آیکون موردنظر (که در UI Tree قابل‌تشخیص نیست، مثل بازی‌های Unity/Cocos) یک مستطیل بکش.
- اون ناحیه به‌عنوان "الگو" (template) در حافظه‌ی داخلی اپ ذخیره می‌شه و یک قانون از نوع `IMAGE` ساخته می‌شه.
- توی حلقه‌ی کلیک، برای این نوع قوانین، آخرین فریم گرفته‌شده با الگو از طریق `Imgproc.matchTemplate` (کتابخانه‌ی OpenCV، نصب‌شده مستقیم از Maven Central، بدون نیاز به دانلود SDK جدا) مقایسه می‌شه؛ فقط اگه شباهت (confidence) بالاتر از حد آستانه (پیش‌فرض ۰.۸۵) باشه کلیک می‌خوره.
- **قبل از استفاده از این قابلیت، باید یک‌بار از اپ اصلی دکمه‌ی «فعال‌سازی ضبط صفحه» رو بزنی و مجوز MediaProjection رو تأیید کنی** — این مجوز هر بار که سرویس ری‌استارت بشه (مثلاً بعد از بستن کامل اپ) باید دوباره تأیید بشه؛ محدودیت خودِ اندرویده، نه باگ.

### 🗂 ذخیره‌سازی سناریوها (چند قانون: «اگه X رو دیدی، Y کار رو بکن»)
- یک صفحه‌ی جدید «مدیریت سناریوها» اضافه شده. هر **سناریو** یک اسم، یک فاصله‌ی زمانی بررسی، و یک لیست مستقل از قوانین داره.
- می‌تونی چند سناریوی جدا بسازی (مثلاً یکی برای یک بازی، یکی برای یک اپ دیگه)، هرکدوم رو تغییرنام بدی، کپی بگیری، یا حذف کنی.
- فقط قوانینِ **سناریوی فعال** (اونی که روی صفحه‌ی «مدیریت سناریوها» انتخابش کردی) توسط حلقه‌ی کلیک اجرا می‌شن — صفحه‌ی «مدیریت قوانین کلیک» قبلی هم دقیقاً همین سناریوی فعال رو نشون می‌ده و ویرایش می‌کنه، بدون تغییری در نحوه‌ی کارش.
- قوانین قبلی‌ات (از فاز ۲) خودکار به یک سناریوی پیش‌فرض مهاجرت می‌کنن؛ چیزی از دست نمی‌ره.

⚠️ **نکته‌ی مهم:** کد OpenCV/MediaProjection این‌جا نوشته شده ولی چون این محیط به Android SDK/شبیه‌ساز دسترسی نداره، امکان build و اجرای واقعی برای تست نبود. حتماً قبل از استفاده‌ی جدی، در Android Studio باز کن، Gradle Sync بگیر (نیاز به دانلود دیپندنسی OpenCV از اینترنت داره) و روی یک گوشی واقعی تست کن.

## این فاز چیه؟ (مستندات فاز ۲ - بدون تغییر)
روی پایه‌ی فاز ۱، حالا اپ می‌تونه **المان‌های واقعی صفحه رو تشخیص بده** (نه فقط کلیک کور روی مختصات):

1. با تپ روی دکمه شناور، یک منو باز می‌شه با دو گزینه:
   - **🎯 تشخیص المان (توصیه می‌شود):** لیست همه‌ی المان‌های قابل‌کلیک صفحه‌ی فعلی (خونده‌شده از UI Tree توسط AccessibilityService) نشون داده می‌شه. کافیه یکی رو انتخاب کنی — مثلاً دکمه‌ای با متن "ادامه" — و یک **قانون** بر اساس متن یا شناسه‌ی همون المان ساخته می‌شه.
   - **📍 نقطه‌ی ثابت:** همون روش کور فاز ۱ (برای مواقعی که المان قابل‌تشخیص نیست، مثل بازی‌های Unity).
2. با نگه‌داشتن دکمه شناور، حلقه شروع می‌شه: هر چند صد میلی‌ثانیه یک‌بار، برای هر قانون فعال چک می‌شه که آیا المان هدف **الان روی صفحه هست یا نه** — فقط اگه بود کلیک می‌خوره؛ اگه صفحه عوض شده و اون دکمه نیست، رد می‌شه و صبر می‌کنه دور بعد.
3. یک صفحه‌ی "مدیریت قوانین" اضافه شده (از منوی اصلی اپ) که می‌تونی همه‌ی قوانین ساخته‌شده رو ببینی، خاموش/روشن کنی، حذف کنی، و فاصله‌ی زمانی بررسی رو تنظیم کنی.

⚙️ تشخیص از طریق **UI Tree** انجام می‌شه (نه پردازش تصویری/OpenCV) — یعنی سبک و سریعه، اما فقط روی اپ‌هایی جواب می‌ده که اطلاعات Accessibility رو درست expose کنن. اپ‌های ساخته‌شده با Unity/Cocos یا بازی‌هایی که UI رو مستقیم روی کانواس می‌کشن، معمولاً چنین اطلاعاتی نمی‌دن — برای اون‌ها فاز ۳ (تشخیص تصویری با OpenCV) لازمه.

## چطور بازش کنم؟
1. Android Studio (نسخه Hedgehog به بعد) رو نصب کن.
2. `File > Open` و پوشه `AutoClickerPro` رو انتخاب کن.
3. بذار Gradle Sync خودش دیپندنسی‌ها رو دانلود کنه (نیاز به اینترنت داره).
4. یک گوشی/شبیه‌ساز با Android 8 (API 26) به بالا وصل کن و Run بگیر.

## جریان استفاده (تست فاز ۲)
1. اپ رو باز کن → دکمه "اجازه نمایش روی سایر برنامه‌ها" رو بزن → مجوز رو بده → برگرد.
2. دکمه "فعال‌سازی سرویس Accessibility" رو بزن → توی لیست سرویس‌ها دنبال **AutoClicker Pro** بگرد → روشنش کن.
3. برگرد به اپ، دکمه "شروع" رو بزن.
4. یک اپ دیگه رو باز کن (مثلاً یک بازی یا اپلیکیشن ساده). دکمه شناور صورتی رو می‌بینی.
5. روش تپ کن → گزینه‌ی "🎯 تشخیص المان" رو بزن → لیست دکمه‌ها/آیتم‌های قابل‌کلیک صفحه‌ی فعلی نشون داده می‌شه → روی موردی که می‌خوای تپ کن.
6. اگه لازمه چند قانون دیگه هم اضافه کن (مثلاً چند دکمه‌ی مختلف که ممکنه توی مراحل مختلف ظاهر بشن).
7. دکمه شناور رو **نگه‌دار** (long press) تا حلقه شروع بشه؛ حالا اپ فقط وقتی اون المان‌ها رو **ببینه** روشون کلیک می‌کنه.
8. برای مدیریت قوانین (حذف/غیرفعال کردن/تنظیم فاصله‌ی زمانی)، از اپ اصلی، دکمه‌ی "مدیریت قوانین کلیک" رو بزن.

## نکات مهم امنیتی/فنی که باید بدونی
- گوگل‌پلی برای اپ‌هایی که از Accessibility Service استفاده می‌کنن سخت‌گیری زیادی داره (باید توضیح بدی چرا لازمشه)؛ برای استفاده‌ی شخصی/تست مشکلی نیست ولی برای انتشار عمومی باید سیاست‌های Google Play رو بخونی.
- بعضی اپ‌ها (بانکی، بازی‌های آنتی‌چیت‌دار) صفحه‌شون رو در برابر Accessibility/MediaProjection محافظت می‌کنن (`FLAG_SECURE`) — روی اون‌ها این روش اصلاً کار نمی‌کنه.
- مصرف باتری/CPU حلقه‌ی تشخیص تصویری قابل توجهه؛ حتماً باید فاصله‌ی زمانی مناسب (نه خیلی کم، مثلاً ۱۰۰۰ میلی‌ثانیه به بالا) بین چک‌ها بذاری، مخصوصاً وقتی چند قانون IMAGE هم‌زمان فعاله.
- مجوز MediaProjection دائمی نیست: هر بار که `ScreenCaptureService` از نو استارت بشه (مثلاً بعد از force-stop کامل اپ یا ری‌استارت گوشی)، باید دوباره از اپ اصلی «فعال‌سازی ضبط صفحه» رو بزنی.
- الگوهای تصویری (screenshot crop) به‌صورت فایل PNG در حافظه‌ی داخلی اپ ذخیره می‌شن؛ اگه اپ رو uninstall کنی همه پاک می‌شن.
